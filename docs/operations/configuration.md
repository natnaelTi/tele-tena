## Independent Alert Runner

Run under the Bench user, using its Python, outside application/RQ workers:

```bash
cd /home/smcs/frappe-bench
env/bin/python apps/tele_tena/scripts/operations_watch.py \
  --bench /home/smcs/frappe-bench --site teletena.selfmadecs.com --once
```

Without `--once` the runner polls30seconds, protected by a site-private flock. It
requires an operator-managed persistent launcher before relying on it after reboot.
No existing Supervisor configuration is regenerated by the application. Alerts remain
disabled initially. Critical widespread booking/payment failures trigger immediate
configured mobile/email attempts; recurring incidents group, cooldown and acknowledge;
recovery is once per incident episode. Sending claims persist before I/O; ambiguous
outcomes are Unknown, not blindly resent or called delivered. Daily08:00 Nairobi
summary is neutral and contains no report contents. Technical outage detection also
needs independent external monitoring because a local runner cannot survive host loss.

Opt-in test: first confirm the owner recipient/chat privately, inspect configured
channel capabilities, explicitly enable alerts, then create a controlled synthetic
incident on a disposable site. Verify one receipt on both channels, acknowledgement,
cooldown and recovery, then restore flags. Record API acceptance separately from
actual receipt. No live test was performed for this release.

No external monitors have been created or verified.

## Private Native Identity Key

If a fresh site has no framework encryption key, operations creates its own random
`private/teletena-operations/actor-hmac.key` (600) under a lock. It never writes or
replaces framework/provider credentials. Keep that key in the private-state backup;
changing it changes pseudonymous continuity. Existing sites with a framework key
continue using it unless an existing operations key already establishes continuity.
